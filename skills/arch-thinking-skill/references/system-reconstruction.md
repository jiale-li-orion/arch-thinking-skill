# 从代码重建产品与技术现状

用户要求全面梳理已有系统、接管文档混乱的代码库、反推 PRD／技术设计，或要求逐模块展开时加载。此时交付责任是覆盖约定范围的系统解释；局部功能、Debug 和重构继续按[任务路由](task-routing.md)选择操作。调查方法沿用[语义追踪](flow-tracing.md)，文档职责、制图与维护沿用[知识维护](knowledge-maintenance.md)。

## 确定覆盖范围与事实基线

从源码入口建立模块清单：产品页面与路由、用户角色、业务实体、服务入口、后台任务、外部依赖和主要存储。把它们按业务职责归并，记录各项的证据入口、负责正文和当前展开程度。覆盖清单放入已有目录或 STATE；正文目录承接读者导航。用户要求全系统时，逐项覆盖清单；热点、近期故障和 PR 决定调查先后。

先用一条完整行为建立初始模型，再逐模块恢复其余职责。追踪中发现旁路、另一个写入者、隐藏页面或历史实现时，将其归入清单并补充对应关系。主链路、管理后台、辅助端和后台作业按各自真实职责展开，范围收敛依据来自入口与读写者，而非最初选中的几条链路。

固定本次源码提交与工作树差异。已有文档提供术语、历史意图和搜索线索，当前行为由源码选择、状态读写及消费者确认；用户明确指定为约束的设计承接预期行为。用户声明旧文档过期或混杂时，先恢复代码行为，再对照旧说法的具体差异。接口声明、目录命名和规范化外观提供候选结构，实际调用及解析路径决定模型。

近期 PR／issue 适合定位反复变动的状态交接。将涉及的改动映射到当前实现、对象身份及恢复入口；已合入、开放分支和运行反馈各按其版本与来源解释。源码支持的行为直接陈述；推断写出触发条件及可能后果。按用户限定的源码范围交付时，正文聚焦源码事实，影响判断的环境问题留在 STATE 或对应调查项。

## 用业务对象连接各份文档

文档职责由[知识维护的职责表](knowledge-maintenance.md#职责与按需读取)承接，实际文件名沿用项目入口。全局总览保持可扫描；产品模块和技术模块承担详细解释；跨模块流程承担分散在多处的身份、提交点和恢复关系。

模块命名先读前端菜单、页面标题、按钮与业务实体。多端叫法不同但指向同一对象时，建立一次术语对应；页面描述继续使用该端文案，技术正文保留准确实现名。纯服务或基础设施以其调用方和消费对象命名。

PRD 与技术设计按业务对象和规则互相映射：产品章节指到实现该规则的具体章节，技术章节标明受影响的页面、操作和结果。映射可以是章节链接、现有规则编号或表格，优先复用现有命名。将“改什么规则 → 哪些页面和实体 → 哪些写入及消费者 → 技术章节”放入变更索引；按对象共享关系继续追到跨模块 flow。

新需求在独立分析条目中连接这些现状关系，记录已确定规则和仍需决策的作用域。现状解释保持本次基线的实际行为，候选设计承接未来变化。

## 产品模块写到可逐项对需求

沿页面和业务实体组织正文，逐小节补足代码中已有的行为差异。以下维度按模块实际内容展开；同一简单规则可以在一段话内解释，存在独立分支时继续分节。

| 阅读对象 | 需要恢复的产品细节 |
| --- | --- |
| 页面与角色 | 谁能进入、从哪进入、与相邻页面的关系、数据归属和可见范围 |
| 字段与素材 | 字段含义、选项、默认值、必填与联动校验、时间／单位口径；素材来源及生效时点 |
| 查询与展示 | 检索匹配方式、筛选与分页、列表／详情读取范围、统计分母、当前值与历史快照 |
| 操作与状态 | 按钮出现及可用条件、操作前后可见状态、保存的业务实体、下一步入口 |
| 异常与再次进入 | 加载、空态、失败、部分成功、结果待确认时的页面行为；保留输入、再次提交、恢复与退出后的结果 |
| 跨页面影响 | 本页写入由谁继续使用，同名“完成／当前／有效”在其他页面的具体范围 |

产品细节由前端和服务端共同恢复：页面文案解释用户看到什么，服务端准入、持久化与查询解释操作究竟形成什么结果。PRD 保留会改变业务判断的身份与状态区别；实现过程由技术章节承接。

例如“传输完成”要展开本设备文件、服务端单文件归档与整任务回执各自的范围、判定和显示位置。只写“支持上传和重试”时，继续追本机列表来源、单文件操作条件、归档确认与任务聚合，直到需求方能够逐项核对这些规则。

## 技术模块写到可解释内部机制

对每个模块沿真实入口、实现选择、权威写入和最终消费者追踪。依赖注入、插件注册或动态装配的路径，从使用方追到绑定条件、实际实现及实例生命周期；多实现共存时核对各入口采用的绑定。职责名称下出现多个状态所有者或独立生命周期时，继续拆到能解释它们如何交接的层次。大文件中的混合职责、跨层调用及共享写入按实际关系建模。

| 阅读对象 | 需要恢复的技术细节 |
| --- | --- |
| 入口与选择 | 调用方、依赖注入的接口与实际绑定、注册或构建接入、配置／角色／数据版本选择、旁路及后台入口 |
| 对象与存储 | 业务身份与尝试身份、版本、权威数据与副本、当前值与冻结值、读写者 |
| 状态与时序 | 前置条件、状态转换、事务与提交点、异步交接、确认语义、最终可见结果 |
| 失败与恢复 | 哪一步已经产生副作用、恢复者读取哪份持久事实、复用什么身份、迟到结果怎样裁决、资源何时释放 |
| 并存实现 | 各自生效条件、输入输出与文件／数据边界、共用状态、历史读法及下游兼容 |
| 改动影响 | 哪个调用方依赖此条件，修改后哪些页面、任务、旧数据和后台消费者随之变化 |

每个存在内部交接的业务模块提供模块图；涉及独立状态、异步提交或恢复时补相应状态图／时序图。按一个需要判断的问题拆图，同一视图可以承接多个相关小节。图中已出现的复杂节点若仍遮住关键写入、选择条件或恢复责任，继续下钻。

正文沿图解释正常推进、关键分支、恢复和消费者；每段承担一组相连机制，段数随关系展开。路径与符号链接用于核对精确条件，模块正文直接说明这些位置怎样共同形成行为。

## 跨模块恢复与复杂度

跨模块 flow 以同一对象贯穿多个写入者，展示各自提交点、确认和恢复依据。需要比较多种恢复时，可使用“中断位置 → 恢复执行者和读取点 → 复用身份及继续条件 → 页面结果”的对照。用户动作、客户端会话、服务端状态、持久作业和资源产物按其真实生命周期连接。

多套实现的风险落在具体交接上：哪些分支共写状态，哪些消费者把同名完成当成不同保证，旧请求何时仍能写入，新尝试如何接续旧文件，后台重试与前台操作怎样竞争。近期反复修复的 PR 作为这些关系的调查线索，代码确定当前机制。

在总览放模块风险定位，按状态所有者数量、跨端交接、并存分支、共享写入和恢复边界说明风险来源，并链接模块正文。代码规模与修改频率辅助安排顺序；风险判断须指出触发变化、传播关系和可见后果。用户当前要求现状重建时，交付这些影响依据；具体修复方案随其后续任务展开。

## 用样本校准深度与交付

用户提供满意样本时，先提取它承担的职责和解释粒度：哪些模块各有独立章节，页面细到哪些动作，哪些状态分别说明，跨模块关系怎样进入图与正文，如何从产品规则找到技术边界。将这些维度应用于本次系统的实际模块。样本的字数、图数和章节编号只反映该系统规模，语义覆盖决定本次篇幅。

一套可用于需求讨论和技术评审的现状文档，应能从目录进入任一约定模块，在正文回答具体行为，再沿关系定位变更影响。逐项完成覆盖清单；有实质分支的模块拥有相应说明与视图，简单模块仍具备入口、读写和消费者的解释。

交付前做两种走读：

1. **按模块检查覆盖。** 对照源码入口和模块清单，检查页面动作、实体规则、内部机制、并存实现及恢复关系是否都有负责正文。目录条目应能到达解释，图的关键边应能回到依据。
2. **按变化检查解释力。** 从一个产品规则进入 PRD，再到技术模块和 flow；改变该规则，检查文档能否推出受影响的写入者、消费者、旧数据与恢复行为。再从后台结果反查生产路径，核对同一身份、状态和口径。

可用的判别场景包括：同一按钮触发两次持久写入，第二次响应丢失后再次提交；两个客户端显示同名完成但读取不同范围；新顺序使原来只出现一次的资源切换需要反向恢复。正文应能据自身条件解释这些差异。若仍需重新发现某个状态所有者或补猜实现选择，沿该缺口补追代码和正文。

引用检查确认证据可定位，渲染检查确认图表可读，语义走读确认行为与影响能被解释。完成汇报指出已覆盖的职责和仍影响判断的具体边界；页面数、文件大小及引用数量用于辅助盘点。
