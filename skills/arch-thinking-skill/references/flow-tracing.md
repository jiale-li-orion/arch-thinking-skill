# 从实际路径追踪语义与系统责任

用于代码定位，以及跨模块、异步、持久化、外部服务或多套实现影响行为的任务。搜索需要调整线索和范围时读取下一节；追踪行为时结合相关架构与契约继续向下阅读。

## 先找到实际入口

用 `rg --files` 定位候选文件，用 `rg -n` 搜索界面文本、API 路由、事件名、配置键、日志或符号。阅读命中附近完整逻辑，再查调用者与消费者。沿别名、注册、依赖注入和动态加载确认运行时选择；代码生成、反射或外部 SDK 需要继续读取对应生成源、注册配置或接口语义。

对具体实例固定业务身份、版本和环境。先从架构猜测责任边界，再用源码及运行证据修正；从局部发现新的写入者或异步任务时，回到相关模块关系。

对同名能力并存的系统，搜索结果先当候选：追用户入口实际选择的实现、调用条件与部署版本，再确认它是否写入权威状态、是否有后台路径覆盖、最终由哪个消费者读取。静态调用存在、当前配置可达和生产环境实际命中各自核对。调查从能解释该实例的路径开始；出现共享机制或公共数据影响时，沿真实依赖扩大范围。

## 用搜索推进理解

**一次搜索应解决一个具体信息缺口，并让下一次读取更有依据。** 例如“页面从哪里取得这个值”“谁把任务标为完成”“当前配置选择哪个实现”。已有路径线索时直接从该边界读起；只有业务描述时，先用界面文案、路由、错误文本、配置键或数据字段找到入口，再从源码取得准确符号。rg / grep 承担工作树中的即时定位，架构记忆提供方向，完整代码和运行事实支撑判断。

### 让问题决定搜索形状

下面的目录与符号是示例，执行时换成仓库中的实际路径。先确认搜索根目录；选择能回答当前问题的最小已知范围，获得新依赖后再扩展。

| 当前需要 | 搜索动作 | 怎样使用结果 |
| --- | --- | --- |
| 找文件或实现族 | `rg --files -g '*order*'` | 先看实现分布，再选入口、公共层及相关配置 |
| 找具体字符串 | `rg -n -F -e 'order.created' -- src/ config/` | 字面匹配事件、路由和错误文本，保留路径与行号 |
| 看大量命中的文件分布 | `rg -l -F -e 'OrderState' -- src/` | 按定义、生产、消费、注册等职责选文件，再读内容 |
| 在确定文件中定位符号 | `rg -n -w -e 'save_order' -- src/orders.py` | 用定义、调用与导入关系核对身份；词边界匹配提供词法候选 |
| 查看局部上下文 | `rg -n -F -C 6 -e 'order.created' -- src/orders.py` | 上下文用于定位，随后读完整分支、函数及异常收尾；读取范围随语义边界调整 |
| 追多个已知别名 | `rg -n -F -e 'order_id' -e 'orderId' -- src/` | 对照转换位置，确认它们指向同一业务对象及版本 |
| 查已跟踪文件中的字面内容 | `git grep -n -F -e 'order.created' -- src/` | 适用于 Git 跟踪内容；普通目录可用 `grep -r -n -F -e 'order.created' src/`，结合各工具的遍历规则解释覆盖 |

输出过多时先改为文件列表，或按路径、文件类型、完整符号和相邻条件收窄。工具截断和 `head` 提供的是预览；需要调用方覆盖时，重新取得相关范围内的完整结果。独立线索可以批量查询，后继查询采用刚读到的名称、数据转换与依赖。

结果为空时先核对搜索条件：工作目录、版本、拼写、大小写、正则含义，以及路径过滤。rg 默认过滤忽略文件、隐藏路径、二进制内容，并跳过符号链接遍历；查清目标位置后，在相关目录按需使用 `--hidden`、`--no-ignore` 或 `--follow`，过滤原因可用 `--debug` 查看。生成代码继续追生成源与构建产物，外部包继续核对实际安装版本。命令报错按错误处理，搜索完成后的空结果按已覆盖范围解释。参数语义以 [ripgrep 官方指南](https://github.com/BurntSushi/ripgrep/blob/master/GUIDE.md)为准。

### 从一个命中跨到下一段机制

搜索词随业务对象经过的边界变化。例如“订单一直处理中”：页面文案定位展示条件，字段来源定位查询接口，接口读取得到存储字段，再沿字段写入追到 worker；worker 的订阅注册和事件名继续连接生产者。每一步都核对身份、转换和选择条件，并从生产者正向读回消费者。这样才能解释为何这个页面会看到该状态。

如果一直命中同一组文件而问题仍悬着，明确缺的是哪条关系：调用绑定、数据转换、状态写入还是实际执行顺序。名称差异通过导入别名、序列化映射、注册表和配置恢复；类型或继承关系复杂时可借助已有语言服务或静态分析；只有业务含义线索时可借助已有语义检索寻找候选，再回源码确认。工具选择服务这条缺失关系，基础工作流保持轻量。

**定位原因与界定影响面承担两种搜索责任。** 前者逐步缩小故障机制，后者从拟改变的保证向外查调用方、共享读写者和生命周期。找到责任函数后，接着按本页“回到修改与验证”判断修改边界。长期记忆保存已经确认的关系、适用条件和证据入口，当轮关键词尝试留在工作过程。

### 将候选变成可用证据

探索阶段按可能的责任路径保留候选；进入修改或交接时，提供当前判断所需的源码位置、关联理由、触发条件及仍影响选择的分歧。调用方、配置和消费者即使保持原样，也可能是决定修改边界的关键证据。候选排序决定下一步优先读什么，修改边界由契约及真实依赖决定；新证据引出其他路径时继续扩展。

多个候选需要跨步骤比较或接续时，在现有任务记录中保留“位置 → 源码事实 → 与当前问题的关系 → 下一项区分证据”。源码事实与任务推断分别表达：函数职责可以保持稳定，它对这次故障的解释力会随新事实变化。只保存仍会改变行动的分歧，判断得到裁决后原位更新。

## 同时追控制、数据与生命周期

| 关系 | 要找的具体证据 |
| --- | --- |
| 控制 | 谁触发，条件分支和配置如何选择实现，谁负责下一步 |
| 数据 | 输入来源、身份与版本，字段转换、单位、序列化，最终消费者 |
| 状态 | 权威值在哪里，全部相关写入、重置、删除、缓存及持久化路径 |
| 生命周期 | 创建、交接、等待、重试、取消、提交、完成、释放与恢复 |
| 承诺 | 返回、ack、回调或事件各说明哪一步完成，调用方如何使用 |
| 资源 | 线程或任务、连接、缓冲、队列与锁由谁持有，何时释放 |

保留有行为意义的边界，一行可以覆盖多个简单函数。必要时画序列图或状态图：标出参与者、状态所有者、同步或异步交接、确认和失败分支。重复排查的链路可保存到 `flows/` 或项目已有位置。

## 从读写和使用方式恢复隐含契约

从当前行为选择相关边界，按下列方向交叉阅读；调查结果放回现有模块、链路或任务正文。

| 从哪里读 | 恢复什么条件 | 怎样确认承担者 |
| --- | --- | --- |
| 调用返回后的分支、下一次调用及界面更新 | 调用者把返回解释成接受、提交、完成还是可见 | 对照被调用者的返回点、提交点和异步交接 |
| 校验、状态读取、锁与事务、条件写入 | 执行需要什么前提，前提需要维持多久 | 查建立条件的位置及期间可改变它的写入者 |
| 赋值、默认值、序列化与消费者 | 字段的业务身份、版本、顺序、单位和缺省含义 | 双向查生产与使用，追转换中保留的区别 |
| 重试、取消、异常退出、重启恢复 | 操作身份、副作用、完成和释放的边界 | 查重复进入时读取的状态及资源接续责任 |
| 旧入口、后台任务、迁移与外部客户端 | 已有行为为何成为兼容依赖 | 查真实使用依据、数据约束及已批准契约 |

例如调用者收到 `save` 返回就读取结果：调用者依赖写后可见；继续追 `save` 实际是提交还是入队、读取采用哪份数据、可见性由谁保证。这样得到的契约包含双方及中间条件。对外部组件，读取实际使用版本的接口语义，并结合调用参数确认适用条件。

逐项区分“源码显示依赖”“运行实例支持”“设计要求保留”和“需要核对的推断”。历史实现中的偶然行为若已有消费者依赖，写出具体影响后选择保持或迁移。调用方覆盖说明实际检查的入口、注册、读写路径及外部边界，检索范围随共享责任扩展。

## 由机制与证据建立归因

### 恢复同一个事件的因果链

固定业务对象、请求或任务身份、代码与配置版本、环境和观察结果。沿状态来源向前追原因，沿控制与数据传播向后推结果，连接“触发条件 → 路径选择 → 状态变化 → 下游效果”。重试尝试、异步子任务和业务对象分别标识；关联由实际传播的身份、版本、消息交接、读写和同步关系支持。日志时间提供辅助顺序，跨进程顺序结合时钟条件及因果交接解释。

为每条关键因果边指出依据：分支条件决定了哪条执行路径、哪次写入影响了哪个读取、哪个确认释放了下游动作。将症状位置、偏差形成位置和修复责任位置分别落到链上。触发因素、故障产生机制与扩大后果的机制各自描述，组合条件共同保留。

### 让竞争解释决定下一次读取或观测

系统路径尚待厘清时，先围绕具体事实缺口导航：谁读取、谁写入、实际参数来自哪里、哪条配置生效。逐段建立可靠的行为轮廓，再从偏差处形成竞争解释。运行观测也可用于发现事实：例如在调用边界查看对象身份与版本，再据此决定下一段源码读取。这样将“恢复系统怎样工作”和“裁决原因解释”衔接起来。

推理方向与取证方式分别选择，再按信息缺口组合：

| 需要回答的问题 | 取证动作 | 得到什么判断 |
| --- | --- | --- |
| 已知输入经过这段代码会怎样 | 顺着分支、调用和副作用阅读 | 给定条件下的后继状态与应有输出 |
| 当前错误值可能从哪里产生 | 从消费者反查转换、写入者和来源 | 能生成该值的候选路径及触发条件 |
| 本次输入实际走了哪条路 | 沿同一请求观察配置选择、交接与状态 | 实例命中的路径及相邻状态 |
| 本次错误结果由哪次变化带来 | 由对象版本、关联日志或调用栈反查具体写入与交接 | 实例的因果来源及仍需核对的边 |

例如静态阅读发现两个写入者都可生成旧值，下一步在读取边界核对对象版本与写入来源；取得实际来源后，回到对应分支解释该输入为何触发它。若源码已明确局部转换差距，则直接转入修改边界判断。读取、运行观测和验证各自服务当前问题，调查粒度随新证据调整。

候选解释从已追到的代码与状态产生，保留会改变修改决定的分歧。对每项写出“若该机制成立，在这个边界应看到什么；另一机制会看到什么”。优先使用现有源码、配置、日志和数据裁决；需要补观测时选择分歧所在的窄边界。

例如旧值问题可先区分：提交的就是旧值、新值随后被覆盖、读取采用旧副本。检查提交对象与版本、后续写入、最终读取来源，分别更新对应解释。对于当前证据都能解释的机制，注明它们共同支持的行动和仍会改变修复位置的分歧。

同时用正常路径约束解释：若相同代码在其他实例中成功，定位输入状态、配置、负载或交接顺序中使机制触发的条件。选择相关条件可比的实例，并检查观察到的差异具体作用于哪一步。候选机制应解释发生位置、触发条件及正常情形；已有事实与预测冲突时，回到对应前提修订机制，继续继承其他有依据的链段。多个因素共同触发时，明确各因素在组合中的作用。

证据的区分能力取决于它实际记录什么。解释一条成功日志前，读出它位于接受、持久化还是完成之后；使用日志空缺作判断前，核对记录条件、采样、保留、环境及该路径的覆盖。同一事件被多处转述时，沿原始来源判断支持范围。并发问题记录读写版本和交接关系；性能问题对照负载、完成量、等待位置及重试放大过程。

### 用反事实推导修复作用，再按需要验证

沿源码推演：改变候选原因对应的条件、保持相关前提时，哪一步状态转换会改变，结果怎样传播；同时推演合法相邻路径。优先选择能区分解释的验证，重复故障具有时序或环境波动时，结合对应条件解释结果。任何运行干预沿项目环境和用户授权执行。

补丁同时改变多个因素时，将改善归于实际干预组合。增加等待可能改变竞争窗口，重启可能同时改变状态与负载；进一步归因要观察相应中间机制。保留症状改善这一事实，同时准确表达原因解释的证据范围。已有完整语义证据能够支持修复时直接推进，验证按任务与风险选择。

### 将归因转成修改决定

在任务或 PR 中按实际复杂度给出紧凑解释：触发与预期、关键状态变化、支持证据、仍影响选择的竞争解释、修复恢复的保证及影响范围。成熟的局部判断可以用一段话表达；跨模块故障结合带证据的时序或状态图。过程性搜索留在当轮工作中。

## 回到修改与验证

按工程思维中的“最小完整修改与验证”判断证据对边界的支持：实际路径、偏差机制、恢复的保证、受影响依赖都有对应依据。阅读实际调用方与消费者，检查配置、数据版本、后台生命周期和最相关的失败恢复。公共修改覆盖共同契约，边界适配明确局部差异；沿改变的保证检查依赖，直到相关行为重新成立。

剩余分歧若会改变修复位置、数据兼容或恢复行为，继续在对应边界取证；若各解释支持同一项安全修改，可先交付该修改并保留原因判断的适用范围。验证选择由这些机制决定，按[任务路由](task-routing.md#验证与交付)执行。

局部解释改变边界、状态归属、实现选择或共同约束时，更新架构及相关图；仅补充当前任务事实时更新 STATE 或任务记录。证据路径和符号靠近重要判断，图和源码之间保留可追踪入口。

## 方法依据与迁移范围

以下材料提供方法依据与适用范围；上文的命令组合和工作流是本 skill 面向工程任务的迁移判断。

- [FSE 2026：A Grounded Theory of Debugging in Professional Software Engineering Practice](https://arxiv.org/abs/2602.11435)，§2–5：观察 12 位开发者的 17 项真实调试任务，将事实缺口、暂定解释、静态导航和运行观测连接起来。正向／反向描述推理方向，阅读／执行描述取证方式，两组选择可以组合。这里吸收的是调试组织方式，证据类型是小样本质性研究。
- [ICSE 2026：Enhancing Issue Localization Agent with Tool-Interactive Training](https://conf.researchr.org/details/icse-2026/icse-2026-research-track/95/Enhancing-Issue-Localization-Agent-with-Tool-Interactive-Training)，[ToolTrain 稿件](https://arxiv.org/abs/2508.03012)，§3–5、附录 B–C：在结构和符号检索接口上训练多步定位，实验覆盖 SWE-bench Verified 的 Python 仓库。其案例从字段赋值转向保存生命周期，支持随源码证据调整追踪方向。指标以参考补丁改动位置为标签；工程中的修复责任与兼容边界继续按实际契约判断。
- [NeurIPS 2024：SWE-agent](https://arxiv.org/abs/2405.15793)，§3、§5.1：搜索接口消融比较结果总览与逐条翻阅，显示反馈形状会影响 Agent 的探索行为。这里吸收“先看分布、收窄查询、再读语义单元”，具体行数与阈值按当前代码和工具选择。
- [Anthropic：Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)，Context retrieval and agentic search：介绍稳定指引结合 glob／grep 即时读取的工程实践。本 skill 据此保持轻量入口和按需取证；检索工具的选择继续由具体信息缺口决定。

近期定位研究补充：

- [CodeGrep](https://arxiv.org/abs/2608.05886)（2026-08-06 预印本，§3–5）训练 grep／glob／read 检索器，向固定修复 Agent 提供候选文件。实验中的收益主要体现为探索成本；不同检索器同时存在训练与精度差异。这里吸收“按后续任务选择证据形状”，工具选型按目标仓库继续判断。
- [SemNav](https://arxiv.org/abs/2609.31176)（2026-09-25 预印本，§3–4）把关系导航、带源码依据的语义卡片和可修订候选组合起来。其下游修复实验使用检索上下文进行单次修复；候选记忆消融还伴随输出候选数量变化。这里迁移候选及依据的更新方法，由已有任务记录承接；具体图服务和记忆组件按实际需要选用。
