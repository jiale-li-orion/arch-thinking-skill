# 从实际路径追踪语义与系统责任

用于跨模块、异步、持久化、外部服务或多套实现影响行为的任务。先恢复相关架构与契约，再展开本页；普通局部修改按需要选用。

## 先找到实际入口

用 `rg --files` 定位候选文件，用 `rg -n` 搜索界面文本、API 路由、事件名、配置键、日志或符号。阅读命中附近完整逻辑，再查调用者与消费者。沿别名、注册、依赖注入和动态加载确认运行时选择；代码生成、反射或外部 SDK 需要继续读取对应生成源、注册配置或接口语义。

对具体实例固定业务身份、版本和环境。先从架构猜测责任边界，再用源码及运行证据修正；从局部发现新的写入者或异步任务时，回到相关模块关系。

对同名能力并存的系统，搜索结果先当候选：追用户入口实际选择的实现、调用条件与部署版本，再确认它是否写入权威状态、是否有后台路径覆盖、最终由哪个消费者读取。静态调用存在、当前配置可达和生产环境实际命中各自核对。调查从能解释该实例的路径开始；出现共享机制或公共数据影响时，沿真实依赖扩大范围。

## 同时追控制、数据与生命周期

| 关系 | 要找的具体证据 |
| --- | --- |
| 控制 | 谁触发，条件分支和配置如何选择实现，谁负责下一步 |
| 数据 | 输入来源、身份与版本，字段转换、单位、序列化，最终消费者 |
| 状态 | 权威值在哪里，全部相关写入、重置、删除、缓存及持久化路径 |
| 生命周期 | 创建、交接、等待、重试、取消、提交、完成、释放与恢复 |
| 承诺 | 返回、ack、回调或事件各说明哪一步完成，调用方如何使用 |
| 资源 | 线程或任务、连接、缓冲、队列与锁由谁持有，何时释放 |

保留有行为意义的边界，一行可以覆盖多个简单函数。必要时画序列图或状态图：标出参与者、状态所有者、同步或异步交接、确认和失败分支。重复排查的链路可保存到 `flows/` 或项目已有位置。

## 从读写和使用方式恢复隐含契约

从当前行为选择相关边界，按下列方向交叉阅读；调查结果放回现有模块、链路或任务正文。

| 从哪里读 | 恢复什么条件 | 怎样确认承担者 |
| --- | --- | --- |
| 调用返回后的分支、下一次调用及界面更新 | 调用者把返回解释成接受、提交、完成还是可见 | 对照被调用者的返回点、提交点和异步交接 |
| 校验、状态读取、锁与事务、条件写入 | 执行需要什么前提，前提需要维持多久 | 查建立条件的位置及期间可改变它的写入者 |
| 赋值、默认值、序列化与消费者 | 字段的业务身份、版本、顺序、单位和缺省含义 | 双向查生产与使用，追转换中保留的区别 |
| 重试、取消、异常退出、重启恢复 | 操作身份、副作用、完成和释放的边界 | 查重复进入时读取的状态及资源接续责任 |
| 旧入口、后台任务、迁移与外部客户端 | 已有行为为何成为兼容依赖 | 查真实使用依据、数据约束及已批准契约 |

例如调用者收到 `save` 返回就读取结果：调用者依赖写后可见；继续追 `save` 实际是提交还是入队、读取采用哪份数据、可见性由谁保证。这样得到的契约包含双方及中间条件。对外部组件，读取实际使用版本的接口语义，并结合调用参数确认适用条件。

逐项区分“源码显示依赖”“运行实例支持”“设计要求保留”和“需要核对的推断”。历史实现中的偶然行为若已有消费者依赖，写出具体影响后选择保持或迁移。调用方覆盖说明实际检查的入口、注册、读写路径及外部边界，检索范围随共享责任扩展。

## 由机制与证据建立归因

### 恢复同一个事件的因果链

固定业务对象、请求或任务身份、代码与配置版本、环境和观察结果。沿状态来源向前追原因，沿控制与数据传播向后推结果，连接“触发条件 → 路径选择 → 状态变化 → 下游效果”。重试尝试、异步子任务和业务对象分别标识；关联由实际传播的身份、版本、消息交接、读写和同步关系支持。日志时间提供辅助顺序，跨进程顺序结合时钟条件及因果交接解释。

为每条关键因果边指出依据：分支条件决定了哪条执行路径、哪次写入影响了哪个读取、哪个确认释放了下游动作。将症状位置、偏差形成位置和修复责任位置分别落到链上。触发因素、故障产生机制与扩大后果的机制各自描述，组合条件共同保留。

### 让竞争解释决定下一次读取或观测

候选解释从已追到的代码与状态产生，保留会改变修改决定的分歧。对每项写出“若该机制成立，在这个边界应看到什么；另一机制会看到什么”。优先使用现有源码、配置、日志和数据裁决；需要补观测时选择分歧所在的窄边界。

例如旧值问题可先区分：提交的就是旧值、新值随后被覆盖、读取采用旧副本。检查提交对象与版本、后续写入、最终读取来源，分别更新对应解释。对于当前证据都能解释的机制，注明它们共同支持的行动和仍会改变修复位置的分歧。

同时用正常路径约束解释：若相同代码在其他实例中成功，定位输入状态、配置、负载或交接顺序中使机制触发的条件。选择相关条件可比的实例，并检查观察到的差异具体作用于哪一步。候选机制应解释发生位置、触发条件及正常情形；已有事实与预测冲突时，回到对应前提修订机制，继续继承其他有依据的链段。多个因素共同触发时，明确各因素在组合中的作用。

证据的区分能力取决于它实际记录什么。解释一条成功日志前，读出它位于接受、持久化还是完成之后；使用日志空缺作判断前，核对记录条件、采样、保留、环境及该路径的覆盖。同一事件被多处转述时，沿原始来源判断支持范围。并发问题记录读写版本和交接关系；性能问题对照负载、完成量、等待位置及重试放大过程。

### 用反事实推导修复作用，再按需要验证

沿源码推演：改变候选原因对应的条件、保持相关前提时，哪一步状态转换会改变，结果怎样传播；同时推演合法相邻路径。优先选择能区分解释的验证，重复故障具有时序或环境波动时，结合对应条件解释结果。任何运行干预沿项目环境和用户授权执行。

补丁同时改变多个因素时，将改善归于实际干预组合。增加等待可能改变竞争窗口，重启可能同时改变状态与负载；进一步归因要观察相应中间机制。保留症状改善这一事实，同时准确表达原因解释的证据范围。已有完整语义证据能够支持修复时直接推进，验证按任务与风险选择。

### 将归因转成修改决定

在任务或 PR 中按实际复杂度给出紧凑解释：触发与预期、关键状态变化、支持证据、仍影响选择的竞争解释、修复恢复的保证及影响范围。成熟的局部判断可以用一段话表达；跨模块故障结合带证据的时序或状态图。过程性搜索留在当轮工作中。

## 回到修改与验证

按工程思维中的“最小完整修改与验证”判断证据对边界的支持：实际路径、偏差机制、恢复的保证、受影响依赖都有对应依据。阅读实际调用方与消费者，检查配置、数据版本、后台生命周期和最相关的失败恢复。公共修改覆盖共同契约，边界适配明确局部差异；沿改变的保证检查依赖，直到相关行为重新成立。

剩余分歧若会改变修复位置、数据兼容或恢复行为，继续在对应边界取证；若各解释支持同一项安全修改，可先交付该修改并保留原因判断的适用范围。验证选择由这些机制决定，按[任务路由](task-routing.md#验证与交付)执行。

局部解释改变边界、状态归属、实现选择或共同约束时，更新架构及相关图；仅补充当前任务事实时更新 STATE 或任务记录。证据路径和符号靠近重要判断，图和源码之间保留可追踪入口。
