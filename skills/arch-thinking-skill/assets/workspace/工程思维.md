# 工程思维：理解、实现和演进系统

本文件保存可复用的判断方法。具体系统由 ARCHITECTURE 解释，当前任务由 STATE 承接，项目指令由 AGENTS 维护。先读核心方法及原始规则，其他章节按当前问题加载。

## 核心方法

**能够解释一项行为怎样发生、由谁负责、修改后会影响什么，再完成最小完整修改与真实交付。**

同时保留三种依据：设计与用户要求规定预期行为；源码与配置解释给定版本的实现；运行反馈说明特定环境实际发生的行为。出现差异时定位到具体契约、路径或部署条件，再决定修代码、补实现、调整环境或提出设计修订。已批准设计中的实现自由度由 Agent 自主处理；影响产品行为或架构承诺的冲突，带着具体影响和建议向用户澄清。

任务循环是“契约 → 实现差距 → 修改 → 验证 → 交付”。理解循环是“全局关系 → 局部追踪 → 行为解释 → 修正全局”。两者交替推进：理解服务当前行动，真实结果校正系统模型。

**全局指导局部。** 先辨认入口、职责、状态所有者、外部依赖和关键约束，据此选择搜索方向。看到一个函数时，向上查调用条件，向下查消费者和副作用。

**局部修正全局。** 发现新的写入者、实现选择分支、缓存旁路或后台生命周期时，检查受影响的其他链路；边界、责任或依赖改变后，更新对应架构正文和图。调查深度由当前契约及影响面决定，解释足以支持行动时继续实施。

架构理解要能预测具体行为：给定一个入口、配置版本和对象状态，说明请求会经过哪条实现、谁改变权威值、哪个消费者看到结果；改变其中一条边时，指出哪些用户行为、失败恢复或旧数据路径随之改变。图中的模块名只是定位线索，带条件的调用、数据与所有权关系才支撑这样的预测。预测与实际反馈分化时，沿最早发生分歧的边取证并修正全局解释。

## 工程判断规则

1. 先追踪代码语义，再决定是否需要测试；测试不是理解代码的替代品。
2. 如需测试，测试结构应与被修改的架构模块和业务链路同构，验证真实契约、关键状态转换或用户可观察行为。
3. 非必要不新增测试，不用字段检查、Mock 调用或简单 happy path 堆砌所谓验证。
4. 优先做最小完整修改，保持既有接口、数据格式和无关行为稳定。
5. 设计契约与实际实现分别保留；发现冲突时显式处理，不能默默用一方覆盖另一方。
6. 不为每个任务生成总结，不记录无复用价值的探索过程，不默认引入完整代码图谱、向量数据库或大型文档体系。

以下为代理依据这些规则及实际工程场景提炼的判断方法；例子中的条件需要在目标系统核对。

## 从全局模型选择局部追踪

先画出与任务有关的最小系统轮廓：用户入口、运行单元、状态所有者、外部依赖和实际部署版本。选择一条能够产生当前行为的真实路径，确认注册、配置与调用条件，再沿输入、写入、交接和最终消费者追踪。新发现的写入者、旁路或版本分支会改变全局依赖时，回到系统图修正边；局部函数细节留在源码和必要的链路说明。

例如同名 `save` 同时出现在旧 API、后台导入与新页面。先查当前请求实际命中哪条路、哪份存储是权威值、哪个消费者读取结果，再决定复用或修改位置。搜到同名函数只是候选入口；运行时选择和数据生命周期才决定它对本任务的意义。调查达到“能解释当前行为、指出修改责任和关键影响路径”时，就进入实施。

## 用契约差分选择复用、适配或新归属

把批准设计和真实实现分别写成同一条业务路径上的行为条件：入口、输入含义、状态转换、输出、失败与恢复、受影响消费者。逐项标出已有能力、真实差异与证据。旧逻辑契约相合时直接复用；边界格式不同而内部语义相同时显式适配；业务责任相异时保留独立入口，并明确共享机制、状态所有权及并存条件。

例如旧 `save` 会填默认值、发事件并在事务提交后回执，新需求要求保存草稿且延迟发布。直接复用可能提前通知下游；另写整套存储又可能制造第二个权威值。先分开“持久化草稿”与“发布事件”两个责任，检查旧消费者和历史数据，再选择在现有所有者内扩展状态转换、在边界适配，或建立有明确选择条件的新流程。设计契约指向预期，代码和运行证据说明现状；产品含义或数据兼容出现实质冲突时，带着差异与建议处理该决策。

## 从零散实现恢复隐含契约

**理解的单位是带条件的业务行为。** 为当前行为恢复：调用前需要什么、执行期间哪些条件需要持续成立、完成后保证什么、产生的副作用由谁接续。目录、类名和函数名提供检索入口；业务身份、状态转换与责任关系决定哪些代码属于同一条解释链。一个责任可能分散在入口、公共库和后台任务中，一个模块也可能承担多个业务责任。先在认知中恢复这些边界，再按任务选择修改范围。

隐含契约从使用方式中推回：调用者收到返回值后立刻做什么，因此依赖了什么保证；被调用者读取什么状态、进入什么分支，因此要求什么前提；持久化数据和后续消费者又要求什么保持稳定。将双方放在同一对象、版本和执行阶段比较，找出保证与依赖之间的差距。恢复契约时追踪成功路径及与当前行为有关的重试、取消、恢复和并发路径，具体动作见语义追踪参考。

对每项隐含条件，区分**实现依赖**与**应保留的行为承诺**。源码可以显示当前调用者依赖排序、唯一写入者或某个默认值；用户要求、批准设计、外部接口及真实消费者决定它的兼容价值。记录“谁依赖、为何依赖、改变后出现什么行为”，再决定保持该条件、迁移依赖或修订契约。一次成功执行支持对应运行条件下的行为，长期兼容判断继续结合调用方与历史数据。

## 从局部正确推导整条行为成立

模块交接时，上游实际保证需要满足下游执行前提；跨越时间后，继续追查保证怎样保持有效。例如“检查后执行”涉及检查依据在执行时的有效期；单次调用正确还需结合并发写入、重试身份和失败恢复，解释多次调用如何组合。沿业务链逐段追问：哪一步建立了条件，谁可能改变它，哪一步使用它，谁负责维持或重新确认它。

由此恢复系统级约束及承担者：同一业务效果如何控制重复、对象版本怎样贯穿计算与提交、完成确认覆盖哪个阶段、资源怎样最终释放。约束内容由实际业务确定。某项条件缺少承担者时，先识别缺失责任；条件由多个位置维持时，比较它们的生效范围和协调方式。图中显式连接这些保证与依赖，才能从模块关系预测用户行为。

## 归因需要解释状态怎样走到结果

把当前原因判断写成一条可追踪的机制：**触发条件 → 实际路径 → 关键状态变化或交接 → 传播过程 → 用户观察**。分别定位症状暴露处、偏差形成处和适合恢复契约的责任处。业务负载、配置或时序可能触发问题；共享状态、确认语义或恢复规则可能使它产生并传播。这些因素共同解释故障时，保留各自作用。

原因判断需要同时回答“它怎样生成这个结果”和“为什么现有证据更支持它”。源码用于推导给定条件下的行为；运行证据用于核对事件实际经过的条件与路径。竞争解释围绕会改变修复选择的分歧展开，并导出可区分的观察。修复后的结果还要结合修改究竟改变了哪些条件解释：一次同时改变缓存、时序与输入的补丁，其改善支持整个干预组合；更精确的归因需要进一步区分这些作用。

归因深度服务工程决策。局部证据已足以支持一项安全且完整的修复时继续实施；仍会改变修复位置、兼容范围或恢复行为的分歧优先取证。能够解释多条故障路径的共同机制值得回传架构知识，单个运行实例的细节留在对应任务中。

## 从业务行为恢复生产、消费与生命周期

选择一个真实请求、对象或事件，沿“产生 → 转换 → 交接 → 写入 → 读取 → 消费结果”追踪。为它保留业务身份、版本、单位及时间含义；同时追查创建、取消、超时、重试、完成与资源释放。搜索赋值、更新、重置和删除，确定全部相关写入者。

例如文件处理经过上传、对象存储、入队、计算、结果保存和页面展示。检查队列传的是文件还是引用、引用指向哪个版本、重试沿用什么任务身份、结果如何关联用户、临时文件由谁清理。沿同一对象连接这些问题，才能定位断开的责任链。

每次交接同时追两件事：**数据到了哪里，以及接收方承诺完成到了哪一步。** 请求接受、持久化成功、计算完成、下游可见，各有具体确认信号。找到返回语句、事务提交、队列确认或回调，再检查调用方如何解释它。

## 存储、计算与通信一起分析

| 视角 | 具体追踪动作 | 据此作出的选择 |
| --- | --- | --- |
| 怎么存 | 查事实来源、索引与版本、缓存失效、事务提交、保留及删除；追同一对象的所有副本和写入者 | 决定状态归属、读取一致性和恢复方式 |
| 怎么算 | 查工作在哪个线程、进程或设备发生，输入快照、重复计算、批处理、锁与并发范围 | 决定执行位置、隔离方式和资源预算 |
| 怎么通信 | 查序列化、单位、顺序、消息身份、缓冲、重试、确认与取消传播 | 决定交接契约、容量和失败处置 |

例如提高 worker 并发，可能让等待从任务队列转移到数据库连接池。先沿链路观察到达量、完成量、队列年龄、在途工作、锁等待和下游耗时，再决定扩并发、减少重复访问、限流或调整批量。比较使用相同负载与数据条件，并观察下游及恢复过程。

缓存同样需要组合判断：它节省计算或通信，同时增加副本与失效责任。性能改动应解释节省发生在哪里、增加了哪种状态，以及容量或故障下怎样收尾。

## 判断案例：从具体分歧选择动作

### 相同表象，沿机制分开修复

“保存后刷新回到旧值”可能来自写入另一份存储、读取走旧实现、后台同步覆盖或缓存版本滞后。先固定对象身份、版本和环境，分别取得写入结果、后续写入与读取路径的证据。按最有区分力的边界继续追查，再确定修复位置。报错处、首次可见偏差和责任位置分别定位。

### 当前结果相同，保留后续状态的区别

调用方超时可能对应请求尚在排队、执行中或已提交但确认丢失。这些状态都表现为等待结束，重试后的结果却各异。追业务身份、提交点和结果查询路径，判断重试怎样复用已有结果或约束重复副作用；取消则另查停止等待、停止计算和处理已提交结果的契约。

相同机制也约束知识压缩：“任务成功”应保留接受、提交和完成的区别，因为重启、重试与恢复依赖它们。

这也是架构记忆的保真标准。两份说明今天都建议“超时后查询状态”，但一份依据请求仍在排队，另一份依据提交成功而确认丢失；新消费者增加自动重试后，两者会要求相异处置。归并时保存状态定义、提交点、证据和新事件下的分化路径，并在现有架构正文与任务记录中分别承接当前解释和历史依据。

### 消费者结束后，生产者和资源怎样退出

消费者只取部分结果，生产者仍可能阻塞在发送或继续占用资源。追停止信号如何到达各生产阶段，谁等待任务退出，谁释放连接和缓冲。扩大缓冲改变容量；结束协议负责整条生命周期。此例的具体并发机制来自 [Go pipelines](https://go.dev/blog/pipelines)，迁移时按目标运行时和 API 核对。

### 已有能力存在，先定位连接缺口

某功能从管理入口可用，从新页面调用失败。固定输入、身份与环境，比较入口选择、参数转换、权限、配置和最终消费者；据此区分已有能力接入缺口与核心能力差距。先复用成立的路径，再实现真实差异。

### 复用取决于契约，新增逻辑需要归属

一个 save 方法可能隐含事务、默认值、事件发送和调用者身份。列出新需求契约与旧实现实际行为，再选择直接复用、边界适配、共享稳定机制或独立表达业务差异。新增实现同时明确入口选择、数据所有权、现有调用方去向和并存条件。修复公共机制时，沿共享调用关系确定影响范围。

### 局部优化回到全局资源约束

吞吐提高后尾延迟上升，可能因为排队位置改变、锁竞争加重或重试放大。沿同一批工作恢复等待与执行时间，把成功完成量、资源占用和恢复行为共同比较。先定位代价转移，再修改瓶颈机制。

## 最小完整修改与验证

修改边界由行为责任和影响面确定。先指出需要恢复的保证，再比较可行修改位置：每个位置改变哪些前提和效果，谁依赖它们，哪些业务差异需要继续成立。局部适配适合边界差异；多个入口共享的错误状态转换适合在共同责任处修复。**最小按必要责任确定，完整按受影响依赖确定。** 行数、文件数与抽象层级各自只是实现特征。

证据足以支持边界，表现为四个问题已有明确答案：目标路径为何生效；偏差怎样产生或实现差距在哪里；修改怎样恢复保证；受影响调用者、数据及生命周期怎样继续成立。沿调用者反查使用假设，沿共享数据双向查读写者，沿时间查在途任务、旧数据与版本共存。每向外跨越一个边界，核对原保证的恢复与额外影响的承接；据此停止扩展或继续处理。剩余疑点按其会改变哪项决定来选择下一证据。

取证强度随判断内容变化。确定的局部分支可由完整语义路径支持；涉及配置选择的判断需要对应配置；归因到特定线上实例需核对实际运行条件；竞争时序或外部服务语义若仍影响方案，使用对应观测或针对性验证。临时缓解按它实际控制的后果及持续条件交付，原因解释保持证据所支持的范围。

演进方案同时解释中间状态：旧调用方、新实现、历史数据和执行中的工作怎样共存，状态权威何时转移，切换失败怎样接续。比较复用与新路径时，把适配、共同状态、选择入口和旧路径退出责任一起计入。

语义追踪先说明应当发生什么、偏差如何产生、修改怎样恢复契约，再选择必要的验证。复用能够执行真实路径的现有检查；新增测试时，围绕具体模块交接和状态转换，例如提交后确认丢失再重试、旧请求晚于新请求返回。Mock 用于隔离外部条件，关键故障边界由实际实现承担。

界面行为需要观察真实页面，设备和外部服务行为使用相应运行证据。验证结果说明所覆盖的版本、环境和边界。任务按验收完成后进入交付；工程进展体现为可靠行为及明确交付状态。

## 图与记忆保存什么

**架构图承担人类决策接口。** 人类应能从图与相邻正文判断系统当前怎样运行、证据覆盖到哪里、修改会影响什么，再按需追到源码与运行事实。系统图保存运行单元、依赖和主要存储通信；模块图保存职责、接口和状态归属；时序或状态图解释关键交接、并发与恢复。图中重要节点连接代码符号、配置或运行对象，边说明带条件的调用、数据、控制、保证与依赖关系。具体制图、证据和覆盖规则由知识维护参考承接。

长期保存能改变搜索方向、复用选择、修复边界和验证方式的知识。关键选择同时保存成立条件、证据及触发重看的变化。例如增加第二个写入者，会改变原先依赖单写入者的安全判断，即使原函数保持原样。即时排查过程留在当轮工作中，正式正文承接现行解释；版本历史由 Git 和任务记录保存。
